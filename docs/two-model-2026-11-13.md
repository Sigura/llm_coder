## Findings shared with burnish

- Big file jobs (imatrix/quantize on the 148 GB bf16, KLD sweeps over shards) fill the page cache and evict
  DeepSeek's mmapped weights: on Nov 14 DeepSeek fell to tg 5.8 tok/s and 82 tok/s prefill with ~18k major faults/s.
  Before measuring or serving DeepSeek after such jobs: fadvise-drop the job's files, then `25-warm-cache.sh`.

- Split-shard variants (`quant/coder_next_rco.py`: `split_db`, `make_variant`): each candidate type is cut once into
  per-layer-group shards; a variant is a directory of symlinks named `m-0000k-of-0000n.gguf`, loaded by llama.cpp as
  a split model. No file is written per variant. Verified: identical PPL to the source file (see Plan B above).
- `llama-quantize --tensor-type` takes std::regex patterns (b12257 `src/llama-quant.cpp`), so per-layer mixes can be
  built from bf16 directly.
- IQ quants are ~5× slower than K-quants when experts sit in CPU RAM on this Zen1 host; fully on GPU they are fine.
- `opencode run` waits on piped stdin: run it with `</dev/null` in scripts.
- Qwen3.6 in OpenCode fails in very deep `/tmp/...` project paths (invents its own `/tmp/<name>/`), passes under `~`.

## DeepSeek concurrency (Nov 16)

Two DeepSeek sessions at once: one server with 2 slots vs two servers. 512-token coding answer, thinking off; GPUs

| case | setup | GPUs | one stream | two streams at once (each) | two streams total |
|---|---|---|---|---|---|

- A costs nothing for one session and gives a second one at ~62% speed (+24% total throughput). The 128k-per-slot

  the VRAM. Splitting the CPU sockets (B3) is worse for one stream. Decode is bound by CPU memory bandwidth, so a
  second process mostly competes for the same bandwidth.
- Recommendation: A, i.e. `--parallel 2 -c 262144` in `deepseek-v4.1-flash-1017.env`; keep Qwen3.8 and MTP on 2,3.
